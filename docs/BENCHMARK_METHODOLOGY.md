# Benchmark methodology and results

ContextDrop's benchmark exists to make compression claims inspectable, not to advertise a universal savings number. This document records the corpus, measurement procedure, evidence checks, exact results verified on 2026-10-23, and the limits of those results.

## What is measured

Every benchmark case is processed by the real engine three times: once with Conservative, once with Balanced, and once with Aggressive. The original input is identical for all three strategies. Results include:

- original and output UTF-8 bytes;
- original and output Unicode scalar values (reported as characters);
- token counts under a selected tokenizer;
- byte, character, and token reduction percentages;
- omissions by category;
- preservation checks and warnings;
- fallback state and classification.

The benchmark does not call a model, compare model answers, measure downstream task quality, or claim semantic equivalence. Evidence assertions only test that selected strings survive.

## Corpus

The corpus is twelve deterministic, synthetic fixtures generated by `scripts/generate-fixtures.mjs` and described by `fixtures/manifest.json`. It is checked into the repository so a third party can reproduce every number.

## Evidence method

`fixtures/manifest.json` contains a `must_preserve` list per fixture. Each entry is a literal substring that must:

1. exist in the original fixture; and
2. still exist in the processed output.

The runner records one check per substring per strategy. There are 56 checks per strategy and 168 checks across 36 compression runs. "All evidence checks passed" means all 168 substrings were found. It does not mean all other content was preserved, and it does not prove that an agent will reach the same diagnosis.

Checks are case-sensitive exact substring searches. They complement the engine's internal protected-line multiset validation; they are not a replacement for reviewing the diff.

## Commands

Build the workspace and run the complete fixture benchmark with exact tokens:

```bash
cargo build --workspace
cargo run --release -p contextdrop-cli -- benchmark fixtures \
  --manifest fixtures/manifest.json \
  --tokenizer o200k_base \
  --format json > contextdrop-benchmark.json
```

For a human-readable table, omit `--format json`. To count with `cl100k_base` or the labelled heuristic, change `--tokenizer`. Exit code `0` means every critical evidence assertion passed. Exit code `3` means at least one assertion failed.

Windows PowerShell 5.1 redirection can write UTF-16 or add a byte-order mark. If a downstream parser rejects the JSON, capture the process stdout with a UTF-8-preserving wrapper or strip the BOM before parsing. The benchmark itself writes UTF-8 to stdout.

The server exposes the same runner at `POST /api/benchmark` for the dashboard.

## Measurement definitions

- **Bytes:** UTF-8 encoded length of the exact string returned, including omission markers. Original bytes are the fixture file length without any added newline.
- **Characters:** Unicode scalar values, not grapheme clusters or display cells.
- **Tokens:** Exact counts from the local `tiktoken-rs` `o200k_base` vocabulary. These are tokenizer-level counts only. They exclude chat framing, tool schemas, provider-specific serialization, retries, and caching. They are not billing guarantees.
- **Reduction:** `(original - output) / original × 100`, calculated from unrounded counts.
- **Aggregate token denominator:** In the table below, the original token count is summed once per strategy, not three times. This makes each strategy's percentage comparable to its own run over the corpus. The original corpus contains 49,254 `o200k_base` tokens under this accounting.
- **Timing:** `processing_time_ms` measures input validation, classification, transformation, and preservation validation inside `compress`. Tokenizer initialization and counting are excluded. Timing values are not treated as performance claims here; results were verified with a release build on Windows, but performance depends on hardware, build profile, and input shape.

### What the results actually show

- Balanced and Aggressive produce larger reductions than Conservative on repetitive test and build output, as intended.
- Conservative's largest reductions come from exact consecutive duplicates (panic waits, repeated multilingual progress, and similar blocks). It also minifies JSON whitespace, but it does not target passing-test or progress patterns.
- Balanced does not compress the structured HTTP log in this corpus because request IDs differ and there are no qualifying contiguous passing-test or progress patterns. Aggressive's normalized-log grouping does.
- Aggressive can be slightly **larger** than Balanced on the Jest and Pytest fixtures (1,277 vs. 1,221 bytes on Jest; 783 vs. 721 bytes on Pytest) because normalized grouping adds omission markers even when the extra normalization does not pay for itself. The engine returns the smaller candidate if a candidate is larger than the original, but it does not choose the smallest of the three strategies automatically. That choice belongs to the user.
- The dense-source control produced no byte reduction under any strategy. One run (`Aggressive`) recorded a fallback because a candidate did not reduce size; the original was returned. This is a successful no-false-savings behavior, not an evidence failure.
- Across all 36 runs, 168/168 evidence checks passed.
- Conservative has no token increase at the aggregate level, but that is an aggregate fact for this corpus. It is not a guarantee for every individual input or tokenizer. The engine's fallback is based on byte size, not token count.

## Interpretation limits

- The corpus is synthetic and small relative to real agent contexts. Results do not establish savings for arbitrary repositories or logs.
- The fixture checks cover selected high-value strings, not all content. Review the output diff before replacing source evidence.
- Exact token counts depend on encoding, chat framing, tool definitions, and provider behavior not represented here.
- The benchmark does not prove semantic equivalence, answer quality, latency improvements, cost savings, or compatibility with any model. Cost figures, if enabled, are simple input-token estimates.
- Timings from a debug build are not comparable to release builds or other hardware.
- Aggressive mode intentionally risks losing useful non-protected context. Its reduction is not automatically preferable.

## Reproduction checklist

1. Use the checked-in fixture files without editing them.
2. Run all three strategies against the same files.
3. Use `o200k_base` with the pinned dependency to compare with these numbers.
4. Verify every manifest string exists before treating a check as meaningful.
5. Report raw output bytes alongside percentages; percentages alone hide rounding and fallback behavior.
6. Re-run `cargo test --workspace` and the benchmark after changing rules, transforms, or fixture content.

## Baseline version

These are 0.1.0 results. `Cargo.lock` pins the tokenizer and engine dependencies. If the compressor, fixtures, tokenizer crate, or protection rules change, the numbers must be regenerated and this document updated rather than presented as unchanged.
